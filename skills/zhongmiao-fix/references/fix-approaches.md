## 1. 通用原则

- 先查平台已有：`docs/CAPABILITY_INDEX.md`（自带模块真实用词）、`docs/GAME_INTERACTION_PLAYBOOK.md`、同类世界的实现。关键词搜不到 ≠ 没有，换目录/命名再找一遍。
- 优先复用现有求解器（`balanceMath.js`、`coordMath.js`、`angleMath.js` 等）和公共写库出口；公共通道不满足需求时，先说明差异和替代方案要保留的保护措施。
- 真值由代码独立重算，不信任内容里自称的答案。
- 改共享组件前列出调用方，改完逐个验证或说明为什么不受影响。

## 2. 前端渲染 / 交互

- 3D 和无 WebGL 的 2D 降级通常是两个组件，两边都要改、都要验。
- 讲解、答题、答错、重试、换题、最后一题、完成页是不同相位，问题可能只在某一相位出现，修复也可能只该影响某一相位。
- 用户可见文案：`t('key')`，`frontend/src/i18n/translations.js` 里 zh-CN 和 en 同步（有的词条还有第三语言，跟着现有结构走）。这个文件很大，有的工具处理它会卡住，见 `verification.md`。
- 颜色用设计变量，不写死 hex；新增美术素材前先查资源台账。

## 3. 历史内容的兼容修复（接口响应时修补）

适用于「已知旧题缺结构字段」：在读取接口里按精确条件补字段。

- 匹配条件要窄：知识点 + 档位 + 已知题干 + 已有真值都对上才补；已有该字段、题干不认识、与真值冲突时一律不覆盖。
- 修复函数要可重复运行、不修改输入对象；未知内容原样返回。
- 接口和公共写回脚本（例如 `server/scripts/writeback_wording_hotfixes.mjs`）要接同一条修复链，否则写回时会丢。完整服务端回归能抓到这种漏接。
- 没取得的档位（例如某档旧快照没有）不能算已修复，要写进未测。

## 4. 新生成内容：提示词 + 确定性校验

- 只改提示词不算修好：要有确定性校验接进正式流程（`server/src/pipeline/k12/validateUnit.js` 等），新内容不合格就拒。
- 校验要检查**内容本身**（重算出的数值、实际的运算、术语是否出现），不要只检查内容自报的标签或关键词——否则内容没变也能通过（铁律 23）。
- 校验先在旧的坏数据上跑一次，确认会报错（先红后绿）。
- 相邻知识点回归：新规则对哪些知识点生效，范围外的课生成结果不变。
- 校验接入写库漏斗后，其他脚本对同一批行的写入也要满足新规则——在 PR 里写明影响。

## 5. 题目内容修改与整套换题（数据库脚本）

学生走的内容在生产库（`k12_generated_units`），仓库里的 JSON 只是快照或候选。

- 个别文案修改：精确限定到那道题；核对数学含义、错因、讲解、错题本显示、中英文。
- 整套换题：题干、选项、错因都可能变，题号会被复用。只在接口响应时替换会让错题本和旧反思按旧题号读到另一道题，所以用内容更新脚本：
  - 默认离线/只预览，显式 `--apply` 才写；写前备份全部目标行；写后独立读回比对。
  - 只在知识点、档位、完整旧内容匹配时生成候选；认识几种历史版本就列几种，并各有测试。「未匹配」可能是已经更新，也可能是不认识的旧版。
  - 逐行写入时中途失败会停，已成功的行不会自动回滚——写进 PR。
  - 更新 `updated_at` 后旧反思保留、旧题干按项目版本规则隐藏，写清这个副作用。
- **不要为了「补齐测试」把离线命令改成连数据库执行。** 生产写入需要另行确认环境、目标行和授权。
- 替换的题目逐题审：独立求解、每个错误选项的错因是否真能导致该选项、讲解和第 1 题同一概念（铁律 17）、前提条件齐全、示范不等于某道原题、不同档之间有真实的运算差异。可以用审核技能里的 `unit_review.mjs scan` 自查。

## 6. 写测试的标准

- 测试验证学生会看到、操作或得到什么，不只是「函数存在」「源码包含某字符串」。源码契约测试（读源码确认接线）可以补充，但不能单独证明行为正确；注意注释里的字符串不算接线（仓库有 `stripComments` 工具）。
- 先红后绿：拿改前的代码跑新测试必须失败，记下失败条数。
- 用真实快照做回归样本（仓库里的单元 JSON），比自己编的数据更能说明问题。
- 测试文件放在被测模块旁边，命名 `*.test.mjs`（`node --test`）或脚本式自测；看同目录已有测试的写法照着来。
- 在测试或 PR 里写清「这个测试能证明什么、不能证明什么」（例如「不能证明屏上只剩一格，截图见 PR」）。

## 7. 范围纪律

- 只修这个编号说的问题。看到范围外的问题：记下来、在 PR 里列为范围外或告诉用户，不顺手改。
- 一个编号的几个子问题里，有的要等教授决定（提交说明或任务表会写「修法待定」），那部分不擅自做，在 PR 里写明留给谁。
- 用户否决过的方案类型不要换个样子再提（例如遮挡问题里「把场景缩小」）。
