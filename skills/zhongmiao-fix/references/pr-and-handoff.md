## 1. 提交与推送

- 提交前：`git branch --show-current` 确认分支对；`git status` 确认没有混进本机配置（`.env*`）、本地 QA 目录、无关文件。
- 身份用用户自己的 git 账号。本机没配全局身份时，按用户给的姓名邮箱逐条传：`git -c user.name="<姓名>" -c user.email="<邮箱>" commit ...`（`rebase` 等改写历史的命令也要带，否则会中途失败）。
- **不加 AI 协作者署名**（`Co-Authored-By: …` 之类）和「Generated with …」页脚，除非用户明确要求——仓库的提交列表会把它显示成另一个提交人。
- 提交说明按团队惯例：`fix(<范围>): <学生现在看到什么>——<原来哪里错，带具体数字> (<编号>)`，正文写问题、根因、改动、没改什么、先红后绿的数字、范围外。
- 推送到自己 fork 的任务分支：`git push origin qa/<任务名>-pr`。push 钩子里关于缺 `gh` 的提示不影响推送。
- 改写过历史（rebase、修改提交）后，正文里固定 SHA 的截图链接要换成新 SHA。

## 2. 截图怎么放进 PR

截图门禁接受两种：
- 在 GitHub 网页正文里拖入图片，生成 `github.com/user-attachments/assets/...` 链接；
- 把图片提交进仓库（`docs/qa/evidence/<编号>-<主题>/` 或 `docs/qa/screenshots/<编号>-<主题>-<日期>/`，附一个 README 写清入口、尺寸、日期、改前=合并基点/改后=PR head、临时数据有没有提交、这些证据不能说明什么），再用**固定 40 位 commit SHA** 的链接引用：
  `https://github.com/<教授仓库>/blob/<完整SHA>/docs/qa/.../x.png?raw=true`

不接受：本地路径、带分支名的链接（合并后分支被删就 404）、外部图床、「截图已发给某某」。用自动化浏览器开 PR 时如果没法上传文件，就用第二种。纯测试/文档改动可以写一行 `NO-SCREENSHOT: <理由>`。

## 3. 在网页上开 Draft PR

1. 打开比较页：`https://github.com/<教授仓库>/compare/main...<你的GitHub用户名>:<fork仓库名>:<分支>?expand=1`
2. base 选教授仓库 `main`，compare 选你 fork 的任务分支。
3. 先读仓库自动带出的 PR 模板，保留栏目，填真实内容（见第 5 节）。
4. 核对 Files changed：只有本任务的文件；提交数和内容对得上。
5. 选 **Create draft pull request**（按团队要求开 Draft）。
6. 开出后在 PR 页面看 CI，如实更新正文里的验证结果。

用户没明确说「提交」时，做到第 4 步停下，把填好的表单给用户看。仓库是私有的，浏览器需要用户本人登录；不代填密码。

## 4. CI 门禁：哪些会拦你

| 检查 | 要你做什么 |
|---|---|
| `qa-peer-review`（**必需**） | PR 必须由作者以外的人点「Ready for review」。作者自己点就红；补救：转回 Draft，请别人再点一次。 |
| PR Screenshot Gate | 改了 `frontend/`（测试文件除外）就要在正文里放至少一张合规图片，或写 `NO-SCREENSHOT: 理由`。改正文会重新判。 |
| PR overlap gate | 你新增的某行（≥20 个非空字符）和别的 open PR 或已合并内容一字不差会红（防重复 i18n key 之类）；确属正常写 `DUP-OK: 理由`。 |
| Guardian | 开发模式构建要过；前端改动行里不许新增硬编码颜色、JSX 里的裸中文（注释里的中文也可能触发）。 |
| AXIS CI/CD | 改动行 ESLint、前端 `npm test`、各类守卫（写库必须走 `patchUnit`、i18n 词条对齐、大文件）、生产构建、服务端 `test:pipeline`（含写回脚本登记一致性）、英文包中文泄漏、前端相关的 Playwright 闸（遮挡、错答提示等）。 |
| Cross-Agent Review | 只对 AI 命名空间分支（`claude-a…/`、`codex…/` 等）生效，人类 fork 分支显示不适用。 |
| Vercel | 与 /tutor 上线无关（生产在阿里云，push main 时才部署）。 |

检查显示 error 通常是「读不到」，不等于你做错了；推一次或改一下正文可以重新触发。不要用「测试已接入 CI」代替「CI 已通过」。

## 5. 交付物一：PR 标题与正文模板

标题：`fix(<范围>): <编号> <一句话写清学生现在看到什么>`

仓库模板有四栏必须保留：**这是什么改动 / 复用核查 / 同类扫描 / 验证**（不适用就写「不适用 + 一句理由」，不要留空）。在此基础上可以用下面的写法填：

```markdown
## 这是什么改动

<编号> / <知识点或世界>：<一句话：受影响的课程和变化>。

原来：<具体复现：哪课哪档哪题，看到什么>。<涉及数学时给关键推导，例如 y=x−1 与 y=−x+5 交于 (3,2)>
根因：<文件:行号或表达式>，<为什么错>。

改动：
- `<文件>`：<做了什么>
- `<文件>`：<做了什么>
没改：<判分 / 题目 / 其他世界……>

## 复用核查（新建机制/组件前）

查了 `docs/CAPABILITY_INDEX.md` <和同类实现>：复用 <已有模块>。<或：新建 X，因为现有 Y 不满足 Z>

## 同类扫描（bug 修复类 PR 必填）

搜了 <关键词 / grep 命令 / 快照目录>：<共 N 处同类，本次修了 M 处 → 0 处>。
范围外：<未修的部分及原因>，已登记在 <issue / docs/PENDING_DECISIONS.md / 本 PR 说明>。

## 验证

- [x] 先红一次：新测试在改前代码上 <N> 条失败
- [x] 改完复测：<x/x> 通过
- 跑了：<专项测试>；<相关回归>；<前端 build / 服务端 test:pipeline / Guardian / 平台同步>
- 浏览器：<尺寸>，<走了哪些路径，例如三档各做完一遍、答错后重试、2D 降级>
- 未测：<只列与结论有关的限制：正式站、真机、生产库、某档没有快照……>

请重点看：<匹配范围、共享影响、已知副作用、需要决定的取舍>

### 截图

<修前 / 修后 / 必要的窄屏或降级状态，每张一句图注>
![修前 <说明>](<合规链接>)
![修后 <说明>](<合规链接>)
```

写法要点：
- 正文简洁，实验过程留在日志和 evidence README。先红后绿和覆盖率用固定说法：「改前 N 条红，改后 M/M 绿」「16 道 → 0 道」。
- 已存在的失败要写明是已存在的（「干净 main 上同样失败」），不要算成通过也不要算成本次引入。
- 代价和没改善的地方照实写。
- 不写尚不存在的 PR 号；已撤回的旧 PR 过程不写进正文，直接相关的技术来源 PR 可以引用。
- 用户可见的视觉改动加一行美术四铁律评价（温暖疗愈 / 心流交互 / 苹果式直觉 / 先复用再新建：各是加分、无关还是减分）；/tutor 学生可见改动按仓库要求说明对「四支柱」的影响。

## 6. 交付物二：发给 reviewer 的话

用户会把它发到群里或私信。短、具体、能让对方直接开始审：

```text
@<reviewer> 已开 Draft PR 待审核：https://github.com/<教授仓库>/pull/<号>

问题：<原现象一句话，带一个具体例子>。
改动：<只改了哪里 / 几处改动各一句>；<没改什么（例如 UI、文案、判分），所以哪些不用同步>。
验证：
- 新增 <N> 条测试，<x/x> 通过；拿改之前的代码跑有 <k> 条失败，说明测试真能抓到这个问题。
- <相关回归> 全绿；<ESLint / build / Guardian> 通过。<哪一步没跑成、为什么>
- <浏览器：尺寸 + 路径>；修前/修后截图已贴在 PR 里。（没做就写「没在浏览器里实际玩一遍」）
建议审核时：进 <课/档>，<做什么操作>，看 <应该出现/不该出现的现象>。
```

变体：
- 很小的改动（文案、样式）：三四行即可——「<哪处文案/样式>：<改前> → <改后>；原来 <学生遇到的困惑>；zh-CN / en 同步。」
- 有前置/后续依赖：加一句「合并后需要执行 <脚本> 才会更新生产题库」「和 #<号> 改的是同一处，已对齐」。
- 不写 reviewer 的名字，除非用户给了；不替用户决定 @ 谁。

## 7. 交付物三：交接状态

```text
任务：<编号> <一句话>
分支 / 目录：qa/<任务名>-pr  ·  <目录>
HEAD：<短SHA>（基于 upstream/main <短SHA>）
PR：<链接 / 「待提交：比较页链接」>   状态：Draft / 待互审 / 已 Ready / 已合并
CI：<N 成功 M 跳过 / 哪项失败 / 未运行>（<查看时间>）
已测：<专项、回归、浏览器路径与尺寸>
未测：<正式站、真机、生产库、跨版本续做……>
下一步：<谁做什么，例如「搭档审核并点 Ready」「合并后执行 X --apply 并读回」「部署后正式站复验」>
```

区分清楚：本地通过 / CI 通过 / 已合并 / 已部署 / 正式站验证。

## 8. 修订与复审之后

- 收到审核意见：逐条记录处理结果（改了 / 不改及理由 / 待教授决定），补测并更新截图，在 PR 里回复。
- 修订后重新跑相关测试；旧截图受影响的要重拍。正文里的验证结果更新到最新 head。
- 不要自己点 Ready for review；修订完提醒审核人复核。
