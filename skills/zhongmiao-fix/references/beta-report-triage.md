# 核实内测 / 测试员报告

测试员、家长、内测群发来的问题，先判断是不是真 bug，再决定修不修。常见结论有五种：真 bug、看错了、操作误解、已经修过、复现不了。每条都要有证据，结论不靠猜。

## 步骤

1. **逐条拆开**：报告里每个现象单独编号，记下原话、截图/录屏、设备、浏览器（App 内置浏览器 / Chrome / Safari）、账号状态（第几天、是否付费）、课/档/题号。
2. **对照内容原文**：找到那道题在仓库快照或生产库里的原文（题干、选项、答案、错因、提示）。很多「判错了」「提示不对」其实是测试员看错了选项里的数字或字——把截图放大逐字核对选项文字。
3. **查是否已修**：看现象对应的代码最近有没有改过（`git log -- <文件>`），已合并的 PR 是否覆盖；报告时间早于修复上线时间的，标「已修复，待正式站复验」。
4. **按报告的路径复现**：同设备类型、同浏览器、同课同档同题、同样的输入。复现不了时换一两种合理的变体（另一档、另一种浏览器、窄屏），仍不复现就如实写「未复现」并附你的复现记录，不要硬猜原因。
5. **判定并留证据**：
   - 真 bug → 进入修复流程（SKILL.md 第 3 步起）。
   - 看错 / 误解 → 截图标出关键文字，写一句可以直接回复测试员的话。
   - 已修 → 附 PR 链接和合并时间。
   - 未复现 → 写清试过的环境和步骤，请测试员补充信息（录屏、账号、时间）。
   - 属于产品设计、需要教授决定的 → 列出选项和影响，交用户转达，不擅自改。

## 远程云手机 / 真机上的操作技巧

- 云手机画面通常是一个 `<video>`：点按需要先悬停再点击；键盘输入可能传不进去；拖动滚动不稳定时，用脚本在 `<video>` 上派发缓慢的指针/鼠标滑动事件。
- 看不清小字时，把 `<video>` 当前帧画到一个放大的 canvas 上再截图。
- App 内置浏览器能否渲染 3D（WebGL）要实际看一眼，不要假设。

## 报告格式

```text
测试报告核实（<日期>，<环境>）
1. <现象原话> —— <真 bug / 看错 / 已修 / 未复现 / 待决定>
   证据：<截图文件 / 题目原文 / PR 链接 / 复现步骤>
   处理：<已开 Draft PR <链接> / 无需修改 / 待教授决定：选项 A、B>
2. …
```
