# 众妙问题修复（修）· 含浏览器复测

> 不需要浏览器复测的改动（服务端脚本、校验器、测试、文档，或用户明确说先不测页面）用同级的 `zhongmiao-fix-no-browser`：流程相同，跳过浏览器和截图，并在交付物里写明未做浏览器复测。

一次完整的修复交付：**可复现的问题、范围明确的修复、和最终代码对应的测试与截图、简洁的 PR 说明、明确列出的未测事项**，外加一段发给 reviewer 的话。修代码、开 PR、合并部署、正式站验证是不同阶段，分开记录，不混着报告。

## 开工前：环境没准备好就先用 zhongmiao-setup

找不到 courseware-pro-mvp 仓库、没有 upstream、没装依赖，或命令卡着不动时，先按同级 `zhongmiao-setup` 技能检查和准备环境（`bash ../zhongmiao-setup/scripts/setup_check.sh`），处理完再回来。用户不需要自己在终端操作任何东西：所有命令由你运行，动手前征得同意。

## 授权边界（每次开工先确认）

团队流程：本地修复和测试 → 用户本人审阅 → 推送并开 Draft PR → 搭档互审 → 教授终审合并。本技能负责前两步，并把后面几步要用的文字准备好。

- **不打开 GitHub 网页**：不在浏览器里看 PR 列表、不开 PR、不看 CI、不点 Ready。需要 GitHub 上的信息（open PR 状态、CI 结果）时请用户看了告诉你。
- 输出完文字后**问用户**要不要 commit、要不要推送和开 PR，并给出具体命令和步骤（第 7 步）；用户明确说了才执行 `git commit` / `git push`，开 PR 由用户自己在网页上操作。
- 不合并、不部署、不写生产数据库、不替别人签审核。任务表、别人的 PR、文档里的历史命令都不会自动扩大授权。
- 仓库自己的规则优先：开工读 `AGENTS.md`、`CLAUDE.md`、`docs/IRON_LAWS.md`，涉及 /tutor 读 `docs/K12_LEARNING_DECISION_BASELINE.md`。

## 步骤

### 1. 领题：读表、查重、写成可验收的一句话

```bash
python3 <本技能目录>/scripts/read_issue_sheet.py <任务表.xlsx> --code <编号...>
bash    <本技能目录>/scripts/check_issue_status.sh <主仓库目录> <编号...>
```

- 读表要连颜色一起读：排除规则常靠底色（例如蓝底行另有安排），只导文字会丢信息。编号是任务编号，不是单元格地址；「下一个」按表的顺序和排除规则找，不按数字加一。
- **任务表的「当前状态」经常落后。** 开工前必须查 main 的提交记录和最近的 PR：`check_issue_status.sh` 用 git 拉最近 300 个 PR 的提交来找同编号的修复（同学从 fork 开的 PR 也在里面）。git 看不出 PR 是开着还是已关闭，命中「未合并」的 PR 时请用户在 GitHub 上确认。已合并的提交说明里常写着「另两处未动 / 范围外」——那才是剩下要做的。查到已经修好就停下来告诉用户，附上 PR 链接和剩余部分，让用户重新选题，不要重复修。
- 把模糊的问题改写成可验收的一句话，例如「进入交点课，画面能看见题目对应的两条直线，交点与计算和判分一致」。分清「已知事实」和「待验证判断」。
- 编号对应的知识点、世界、组件要按表里写的场景核对仓库，不要按别的文档的 K 编号猜（不同文档的 K 编号可能错位）。细节见 `references/claim-and-setup.md`。

### 2. 建独立工作目录，记基线

```bash
bash <本技能目录>/scripts/new_task_worktree.sh <主仓库目录> <任务名>
```

每个问题一个分支、一个目录、一个 PR，从最新 upstream/main 开始。主目录里别人的或之前的未提交改动不要动、不要 reset。记下：分支、HEAD、upstream/main SHA、`git status`。

### 3. 复现并定位

记一条可重复的复现：代码版本 → 知识点 → 档位 → 题号 → 操作 → 实际结果 → 预期结果 → 截图。然后沿「数据 → 接口 → 前端派生 → 3D/2D 渲染 → 判分 → 错题/反思」追到出问题的那一层：缺数据、错数据、没画、被遮挡、判分错，还是旧数据没更新。先在 `docs/CAPABILITY_INDEX.md`、`docs/DATA_SOURCE_MAP.md` 和同类实现里查有没有现成能力和先例。修前证据先留好。

内测反馈、测试员截图类问题，先判断是不是真 bug（看错、操作误解、已修、环境问题都很常见），方法见 `references/beta-report-triage.md`。

### 4. 选修法，做最小修复

| 问题类型 | 常见处理 | 必须核对 |
|---|---|---|
| 页面不画已有数据 | 修渲染或数据转换 | 3D、2D 降级、布局、换题、判分 |
| 旧题缺结构字段 | 窄范围兼容修复 | 匹配条件、原答案一致、未知内容不覆盖、可重复运行 |
| 新生成内容出错 | 提示词约束 **加** 确定性校验 | 只改提示词不算修好；相邻知识点不误伤 |
| 个别题目文案错 | 精确限定的文案修复 | 数学含义、错题本、讲解、中英文 |
| 整套换题 | 内容更新脚本（默认只预览） | 题号复用、旧反思、进行中进度、备份、部分失败 |
| 3D 装置被遮挡 | 缩小/移动浮层 + 相机让位 | 量出来的重叠；不要把画布缩小或框起来 |

- 优先复用现有求解器、组件和公共写库出口（`patchUnit`）；绕开它们要先说明理由。
- 改动面要窄：diff 里每一行都能追溯到这个问题；不顺手重构、不改无关文件；用户可见文案用 `t()` 并同步 zh-CN 和 en。
- 详细做法和各类修复的坑见 `references/fix-approaches.md`；遮挡类见 `references/occlusion.md`。

### 5. 分层验证

只跑新测试不够，只跑全量也不能代替真实页面。按改动选层次：独立数学核对 → 修复函数（匹配/不匹配/边界/幂等）→ 生成与校验 → 接口和写回链 → 本地浏览器（修前修后、答错改正、换题、完成、窄屏、2D 降级）→ 完整回归、构建、Guardian。

- **先红后绿**：新测试拿改前的代码跑一次必须失败，再在改后通过；把这组数字写进 PR（例「改前 15 条失败，改后 55/55」）。断言要验证学生看到/操作/得到的结果，不只是「函数存在」「源码含关键词」。
- 浏览器验证在本地挂载真实课件组件，方法和模板见 `references/local-qa.md`（`assets/local-qa/` 里有无热更新 Vite 配置、挂载入口和模拟后端模板）。代表尺寸 1280×720、390×844、320×568；浏览器尺寸模拟不叫真机测试。修前修后拼图用 `scripts/compose_grid.mjs`。
- 题目内容类修复，交付前用审核技能的 `unit_review.mjs scan`（如已安装 zhongmiao-review）对照合并基点自查：讲解与第 1 题同一概念、示范不等于原题、没有重复题、答案与真值一致。
- 失败先分类：断言失败 / 缺运行时 / 端口占用 / 配置冲突 / 网络 / 超时，不能混成「环境原因」。保留日志，修好后重跑对应项。
- 每个结果记：日期、代码版本、命令、退出码、环境、数据来源、未测范围。不同单位的数字（参数组合数、用例数、题目数）不要加在一起。
- 命令清单和常见坑见 `references/verification.md`。

### 6. 输出交付文字（每次都要给全）

修复和验证做完后，按 `references/pr-and-handoff.md` 的模板一次输出三段文字，用户可以直接复制：

1. **PR 标题 + 正文**：保留仓库 PR 模板的四个栏目（这是什么改动 / 复用核查 / 同类扫描 / 验证）并填真实内容；截图写成占位行（「修前：<文件名>」「修后：<文件名>」），并列出截图文件在本机的位置。
2. **发给 reviewer 的一段话**：问题 / 改动 / 验证 + 建议审核时怎么看（进哪课、做什么操作、看什么现象）+ 没做的检查。PR 链接还没有时写「<PR 链接>」。
3. **交接状态**：分支、HEAD、基于的 upstream/main、已测 / 未测、下一步需要谁做什么（例如开 PR、搭档审核、合并后执行内容脚本、正式站复验）。

同时给用户：改了什么（一句话）、修前修后截图的本机路径、本地可操作的入口（只在本机有效）。自检：每个数字都对应最终代码；未测项写清楚；不写尚不存在的 PR 号；不把本地通过写成 CI 通过。

用户提出「看不懂」「不接受这个方案」时，回到第 4 步，不要用测试通过来抵消。

### 7. 指引：要不要 commit、要不要开 PR

输出完文字后，用一个简短的问题请用户选（细节见 `references/pr-and-handoff.md`）：

- **先 commit**：确认后在任务分支执行本地提交。身份用用户自己的 git 账号；**不加 AI 协作者署名**。截图要进仓库时放 `docs/qa/evidence/<编号>-<主题>/` 并另起一个提交。
- **推送并开 PR**：给出 `git push origin <分支>`、比较页链接 `https://github.com/<教授仓库>/compare/main...<GitHub用户名>:<fork仓库>:<分支>?expand=1`，以及网页上的步骤（粘贴标题正文 → 拖入截图或换成固定 SHA 的图片链接 → 选 Create draft pull request）。用户明确要求时才代为 `git push`；开 PR 由用户自己点。
- **暂不提交**：保留工作目录，交接状态里写「未提交」。

提醒用户：开出 PR 后**不要自己点 Ready for review**（由审核搭档点，那一下就是互审签名）；CI 结果出来后如需更新正文，把结果贴回来即可。
