# 审核检查清单

按 PR 实际改了什么挑着用，不是每个 PR 都要全过一遍。目标是确认「声称的修复成立、没引入回归」，不是穷举所有可能的失败。

## 目录
0. 这个仓库里审核最常抓到的漏洞
1. 所有 PR 都要做的
2. 前端渲染 / 交互修复
3. 题目、讲解、错因等内容修复
4. 生成提示词 + 校验器
5. 数据库写入脚本
6. 遮挡 / 布局（铁律 20）
7. 测试命令与常见环境坑

---

## 0. 这个仓库里审核最常抓到的漏洞

从已合并 PR 的「审核后补的第二个提交」归纳出来的，先过一遍这几条，命中率最高：

- **常量有镜像**：前端改了容差/阈值，服务端（例如 `server/src/pipeline/k12/worldTolerance.js`）、`validateUnit.js`、手工脚本里还有同一个数没改。`grep -rn "<旧值或常量名>"` 全仓搜。
- **3D 改了、2D 降级没改**（或反过来）。
- **读取时的内容修补没登记到写回脚本**：`server/src/utils/*` 里加了按原文匹配的修补，`server/scripts/writeback_wording_hotfixes.mjs` 也要按同样顺序登记（import、修复链、KP 列表），否则服务端测试会红、写回会丢。
- **写生产库没走 `patchUnit`**：裸 `supabase.update` / fetch PATCH 会被写库漏斗守卫拦；预览要用 `patchUnit({dryRun:true})`，和真写同一套判断。
- **读回比对用了 `JSON.stringify`**：数据库 jsonb 会重排键顺序，必须用 `jsonStructuralEqual`。
- **并发覆盖**：写库脚本没带 `updated_at` 版本条件，别人同时改过就会被覆盖。
- **测试自己比自己**：夹具和被测代码来自同一个常量，改坏了也恒绿。夹具应该用生产原文/真实快照；做一次变异（把修复改回去）看测试会不会红。
- **显示和判分不一致**：滑杆、数字框、草稿值，显示的是一个数、提交判分的是另一个数。
- **删文件没删干净**：删了模块但没 `git rm` 或还有引用，CI 一片红。
- **返回、缩放、换题**：讲解里点「上一步」、窗口尺寸变化、换到下一题后状态有没有恢复。
- **生产数据根本触发不到新代码**：代码没错，但真实内容缺对应字段（例如没有 spec），学生那一屏什么都不会变。拿真实快照或只读生产数据走一遍。
- **同一个问题两人同时在修**：查 main 和 open PR，有重叠就在意见里指出，并说明哪部分以谁为准由教授定。

## 1. 所有 PR 都要做的

- [ ] 记下审的版本：head SHA、合并基点、最新 main SHA（`fetch_pr.sh` 会打印）。
- [ ] PR 正文用用户贴来的最新版；列出承诺清单（改了什么 / 覆盖范围 / 跑了什么 / 写明没做的）。
- [ ] 对照任务表原文：PR 修的是不是这一行说的现象，范围对不对。
- [ ] 同一编号是否已有已合并或 open 的 PR（重复修复要指出）。
- [ ] diff 里每一处改动都能追溯到这个问题；有无无关改动混进来（格式化、别的任务、本地配置文件、`.env*`）。
- [ ] 中英文：用户可见文案改了 zh-CN 是否同步了 en（`frontend/src/i18n/translations.js`），没有在 JSX 里硬编码中文。
- [ ] 与最新 main 试合并是否冲突；main 在基点之后也改了同一文件时，看会不会互相覆盖已合并的修复。
- [ ] CI：用用户贴来的结果（不打开 GitHub），写「N 成功 M 跳过 / 哪项失败」；没有就写「CI：未查看」。Vercel 检查与 /tutor 上线无关（生产在阿里云，`deploy-aliyun` 只在 push main 时跑，PR 上 skipping 正常）。

## 2. 前端渲染 / 交互修复

- [ ] 改动和根因对得上：读改动前后的同一段逻辑，确认原来为什么错、现在为什么对。
- [ ] 找全调用方：`grep -rn "<函数或组件名>" frontend/src`。作者写「3/3 入口」就逐个核对；共享组件（WorldOverlay、FeedbackDock 等）改动影响多个世界时，至少验一个非目标世界没坏。
- [ ] 3D 和无 WebGL 的 2D 降级两条路径都改了吗（很多世界有 `*2D.jsx`）。
- [ ] 答对、答错、重试、换题、最后一题、重看讲解这些相邻状态还正常吗。
- [ ] 视觉改动有截图；截图对应的是最终版本、同一题同一尺寸的改前改后。
- [ ] 源码契约测试（读源码找字符串）只能证明「接上了」，不能证明运行行为正确；行为要有运行时测试或浏览器证据。

## 3. 题目、讲解、错因等内容修复

题目内容错误最容易被「测试全绿」掩盖，必须读实际题目：

- [ ] `unit_review.mjs dump` 打印改后的每个单元，逐题读题干、选项、答案、解析、错因。
- [ ] **独立重算每道题的答案**，不要只跑 PR 自带的校验器（它和题目用的是同一份数据）。
- [ ] `unit_review.mjs scan --base-ref <基点>`：
  - concept-gap：讲解示范讲的概念和第 1 题是否同一个（铁律 17）。易混术语族：对顶角/邻补角/同位角/内错角/同旁内角；平均数/中位数/众数/方差；圆心角/圆周角；SSS/SAS/ASA/AAS/HL；正弦/余弦/正切 等。照示范做第 1 题会不会必然答错？
  - demo-repeat：示范是不是就是某道原题（学生点「重看讲解」能照抄答案）。
  - dup-in-unit / dup-cross-tier：同单元、相邻档有没有同一道题。
  - answer-mismatch：标准答案选项和真值不一致。
  - 每条都打开原文确认；[原有] 的不算本次引入。
- [ ] 前提条件齐不齐：例如用「同位角相等」之前题目有没有说两直线平行；「互补」有没有交代是哪两个角。
- [ ] 题干有没有把答案或方法说破（「先用邻补角…」这种提示是否让题目失去意义要结合档位判断，属教学取舍时交用户决定）。
- [ ] 错因（wrongWhy）是否对应它挂着的那个错误选项真能算出来的错法，而不是泛泛的「少算了 10°」——只在 PR 声称修了错因时作为必改项。
- [ ] 「难度梯度」「换题」类：数一数每档实际要做的运算（不是自报的标签），看声称的提升是否在运算上成立。
- [ ] 整套换题：题号复用会影响错题本 / 旧反思的对应关系，看 PR 有没有说明处理方式（通常是更新 `updated_at` 让旧题干按版本规则隐藏）。

## 4. 生成提示词 + 校验器

- [ ] 只改提示词没有接校验 = 软约束；要看有没有确定性校验接进正式流程（`validateUnit.js` 等）。
- [ ] 校验器查的是内容还是形式？只查自报字段（例如 difficultyRole、reasoningSteps）或关键词时，内容不变也能通过——这种情况下「15/15 通过校验」不能证明内容修好了。
- [ ] 先红后绿：在改前的数据/代码上跑一次，它能报错吗？
- [ ] 相邻知识点是否被误伤（新校验对哪些 KP 生效，范围外的课行为不变）。
- [ ] 新校验接入写库漏斗（`server/scripts/lib/unitWrite.mjs` 的 patchUnit 会调用 validateUnit）后，其他脚本对同一批行的写入会不会被拒。

## 5. 数据库写入脚本

- [ ] 默认只预览（dry-run），显式 `--apply` 才写；写前备份全部目标行；写后独立读回比对。
- [ ] 匹配条件：只在知识点、档位、旧内容完全匹配时才写，未知版本跳过；「未匹配」可能是已更新也可能是不认识的旧版，不能当成没问题。
- [ ] 部分失败：逐行写入时中途失败怎么办，已写的行是否回滚，有没有写清。
- [ ] 走公共写库出口（patchUnit），不绕过它直接 PATCH。
- [ ] 结论里分开写：代码合并 / 脚本执行 / 生产读回 / 正式站复验。审核阶段一般只能对前一项下结论。

## 6. 遮挡 / 布局（铁律 20）

- [ ] 判据是量出来的重叠（像素或几何），不是「看着还行」；作者给了改前改后的测量和截图吗。
- [ ] 竖屏矮机（375×667、390×844、320×568）和宽屏都看了吗；浏览器尺寸模拟不是真机。
- [ ] 解决方式有没有把 3D 场景缩成一小块或硬框住（团队不接受「场景变小但没被挡」的方案，倾向全屏画布 + 相机让位 + 缩小浮层）。
- [ ] 共享布局改动有没有影响其他世界。

## 7. 测试命令与常见环境坑

在审核目录里跑（命令以仓库 `package.json` 和 CI 为准，先看一眼）：

```bash
# 单个/几个测试文件（服务端或前端的 .test.mjs），不连生产库
node --test path/to/a.test.mjs path/to/b.test.mjs
node path/to/selftest.mjs            # 有些是脚本式自测，直接 node 跑

# 前端（frontend/）
VITE_APP_LOCALE= npm test            # 清掉本机强制语言，只作用于这条命令
npm run build

# 服务端（server/）
npm run test:pipeline

# 仓库根目录
bash scripts/guardian/guardian_v5_audit.sh
node scripts/guardian/platform_sync_audit.mjs
git diff --check
```

常见坑（遇到时如实记录为环境问题，不要写成通过或失败）：
- 前端 `npm test` 里有一批浏览器测试会各自起 Vite；多个 worktree 软链同一个 `node_modules` 时共享 `.vite` 预构建缓存，可能互相卡死。先跑非浏览器测试，浏览器测试单独跑。
- 端口被别的进程占用导致测试服务起不来——这是环境问题；换端口或关掉占用进程后重跑对应项。
- 缺 Playwright 官方 Chromium：在 `frontend` 执行 `npx playwright install chromium --only-shell`（先确认确实是这个报错）。
- 本地 `.env.local` 强制中文会让英文断言超时：命令前加 `VITE_APP_LOCALE=`，不要改配置文件、不要放宽断言。
- Guardian 含自动合并/修复步骤：跑之前之后看 `git status`，别把审计产生的改动当成 PR 内容。
- 测试需要 `--experimental-test-module-mocks` 时确认 Node 版本支持。
