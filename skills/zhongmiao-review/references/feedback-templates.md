# 审核文案模板

用户要的是能直接转发、带链接的短文字。默认结构：**状态 + PR 链接 + 问题 + 根因 + 测试结果**。需要细节时再展开。

通用规则：
- 第一行就是结论，PR 链接放正文里（用完整链接，不写裸 `#123`）。
- 问题按编号列，每条一个具体例子：题号 / 原文 / 数值 / 文件:行号 / 复现步骤。
- 「测试结果」只写自己真跑过的；作者或 CI 的结果单独标明来源。没跑浏览器就不写浏览器结论。
- 不写称呼和人名，除非用户给了；`@` 谁由用户自己决定。
- 不写 (d) 类延伸内容（见 SKILL.md 审核口径）。
- 测试数字照实写，不从模板或别人的 PR 里抄数。

---

## 1. 审核通过

```text
PR #<号> 已审核，审核通过。
PR链接：https://github.com/<owner>/<repo>/pull/<号>

问题：<原问题一句话>。本次修复：<改了什么，覆盖范围，例如「三档 15 题」「3/3 个入口」>。

根因：<与实际改动对应的原因>，<修复方式>。改动和根因对得上；涉及 <N> 个文件，没发现多改或漏改。<如重点核过牵连全局的改动，写一句核了什么、用什么真实内容核的>

测试结果：
- 独立重跑：<专项测试名> <x/x> 通过；<相关回归> 通过。
- 浏览器：<尺寸>，<走了哪条路径，看到了什么>。（没跑就删掉这一行）
- CI：<用户提供的结果，例如 All checks have passed / 哪项失败；没有就写「未查看」>。
- 未重跑：<例如全量构建、Guardian>，沿用 CI 结果。

<确有必要时一句下一阶段事项：例如「合并不会更新生产题库，需执行脚本后复验」>
```

更口语的写法（同样合格）：

```text
PR #<号> 审查完成，未发现阻塞合并的问题。
<链接>

问题：<现象>；本次已补齐 <A、B、C>。
根因：<原逻辑为什么错>；现在 <怎么判断>，<没受影响的路径> 保持原样。

测试结果：
- 独立运行 <N> 个相关测试文件，全部通过。
- 补测 <某组件的 N 种状态>，全部通过。
- 已核对 PR 截图；CI（用户提供）：<lint、浏览器测试、构建、Guardian> 均通过。
```

## 2. 需要修改

```text
PR #<号> 已审核，以下问题需修改后再审。
PR链接：https://github.com/<owner>/<repo>/pull/<号>

1. <问题一句话>。例：<具体题号/文件:行号>，<实际看到什么>，<应当是什么>。
2. <问题一句话>。例：<…>。照 <操作> 做会 <结果>（浏览器已复现）。
3. <…>

测试：<专项 x/x 通过>；<独立复算/探针结果>；本地浏览器复现了第 <k> 条；CI <状态>。
```

要点：
- 只列有依据的重点项。修好的部分可以先用一句话肯定（例「<主问题>修好了」），再写没解决的部分。
- 「原问题仍在」要给出和任务原文对照的证据，例如：「挑战档 25 题里 12 题仍只需算一次 180−已知角」。
- 一个问题只举最有说服力的一个例子；同类的再写「另 4 处同样」。
- 建议（非阻塞）另起一行写「建议（不阻塞）：…」，或者干脆不写。

「修好了一半」的写法：

```text
PR #<号> 已 review。
结论：<A 问题> 修好了；但 <测试者看到的 B 现象> 不会消失，<原因一句话>。

修好的部分
<怎么确认的：用改前代码跑出了什么，改后是什么>

没解决的部分
<现象仍在的具体路径和原因>。要解决需要 <方向一句话>，是否在本 PR 处理请 <教授/作者> 决定。
```

## 3. 复审（作者更新之后）

```text
已复核 PR #<号> head <短SHA>，此前要求修改的 <N> 项：
1. <问题1> —— 已解决（<怎么核的>）。
2. <问题2> —— 仍在：<现在的具体表现>。
本次独立重跑 <N> 个相关测试文件全部通过；与最新 main <短SHA> 试合并<无冲突/冲突在 X>。未重跑 <浏览器/生产库/全量构建>。
```

## 4. 发给作者的追问（证据不足时）

```text
PR #<号> 有两处需要确认才能下结论：
1. PR 里写 <声明>，我在 <文件/题号> 没找到对应改动 / 结果不一致（我这里 <实际结果>）。是另有提交还是描述需要更新？
2. <…>
```

## 被问「这是他没做完的，还是你延伸的？」时

逐条回答类别：(a) 声称完成但没完成 / (b) 任务范围内但本次仍保留 / (c) 本次引入的回归 / (d) 我延伸的。(d) 类从转发文案里删掉，再给出删减后的版本。

## 文案之后：告诉用户下一步（不在 GitHub 上操作）

```text
下一步（在 GitHub 上由你操作）：
- 通过：把上面的文字发给作者 / 贴到 PR 评论，然后在 PR 页面点「Ready for review」——这一下就是互审签名，不用另写 Approve。
- 需修改：把文字发给作者，PR 保持 Draft，先不点 Ready；作者更新后把新说明贴给我复审。
```
