# 众妙 PR 审核（审）· 含浏览器复现

> 不需要浏览器复现的 PR（服务端脚本、校验器、测试、文档，或用户要快速过一遍）用同级的 `zhongmiao-review-no-browser`：口径和文案相同，跳过第 5 步，并在结论里写明未做浏览器复测。

审核要回答的只有一件事：**这个 PR 声称解决的问题，在它实际提交的内容里解决了没有；有没有因为这次改动坏掉别的东西。** 产出是一段能直接转发的文字，不是长篇审计报告。

## 审核口径（动手前先对齐）

每条发现都要能归进下面一类，并且被问到时说得出是哪一类：

| 类别 | 处理 |
|---|---|
| (a) 声称完成，实际没完成 | 必须修改，给题号/代码位置/复现步骤 |
| (b) 在任务表这一行范围内，但本次仍保留 | 写「本次仍保留」，不要写成「新增错误」 |
| (c) 本次 diff 引入的回归、数学错误、正常操作失败 | 必须修改 |
| (d) 自己延伸出来的：main 上原本就有的问题、重新设计建议、假想的异常输入/并发/未来生成变体 | **不写进转发文案**；确有价值时单独跟用户说一句，由用户决定 |

- 教学表述、难度安排这类有不同理解的，说明理由交用户判断，不自动升级为阻塞；用户已经接受的取舍，后面不再翻出来。
- 「可以构造出失败」≠「本次修复没完成」；「CI 全绿」≠「内容正确」。判据永远回到任务原文和实际提交的内容。
- 审的是一个具体版本。结论里写「审的是 head `<SHA>`」，作者之后再推就要复审。

## 步骤

### 1. 拉代码，记下版本事实

```bash
bash <本技能目录>/scripts/fetch_pr.sh <主仓库目录> <PR号>
```

脚本会建一个 detached 的只读审核目录，并打印 head SHA、合并基点、提交列表、改动文件、与最新 main 的试合并结果，以及「PR 和 main 都改过的文件」。仓库是私有的，`gh` 不一定装了：PR 页面在已登录的浏览器里看。

### 2. 读 PR 页面，列「承诺清单」

在浏览器打开 PR，读**最新版**正文（用户贴来的可能是旧版，以 GitHub 为准）、所有评论、CI 结论（例：All checks have passed，N 成功 M 跳过；或哪项失败）。同时：

- 对照任务表这一行的原文（问题、现象、涉及知识点）——PR 修的范围要和它对上。
- 查同一编号有没有别的 PR：`git log upstream/main --oneline | grep <编号>`，以及 open PR 列表。重复修同一个问题时，审核意见要指出重叠。
- 把作者声明拆成一张清单：改了什么、覆盖哪些课/档/世界（例：3/3 入口）、跑了哪些检查、哪些写明没做。后面每一项都要有「核实了 / 没核实 / 不成立」。

### 3. 审实际内容（这是审核的主体）

按改动类型选看法，详细检查项见 `references/review-checklist.md`：

- **代码修复**：读 diff，确认改动和根因对得上；找全调用方，核对作者报的覆盖率（例「三个入口共用一个函数」是不是真的）；有没有多改、漏改、顺手改坏别的。
- **题目/讲解内容**：把实际题目打印出来逐题读，独立重算答案，不要拿 PR 自带的同一份数据互相证明：
  ```bash
  node <本技能目录>/scripts/unit_review.mjs dump <单元目录> --ref pr/<PR号> --repo <主仓库>
  node <本技能目录>/scripts/unit_review.mjs scan <单元目录> --ref pr/<PR号> --repo <主仓库> --base-ref <合并基点SHA>
  ```
  `scan` 会把「讲解和第1题术语不一致（铁律17）」「示范就是某道原题」「同单元/跨档重复题」「标准答案和真值不一致」标成 **[新增]** 或 **[原有]**。它只是定位线索，每条都要打开原文读完再判；[原有] 的不算本 PR 引入。
- **校验器 / 门禁**：看它检查的是实际内容还是形式（只查自报的标签、关键词、字段存在 = 形式，内容没变也能过）。拿改前的代码跑一次，确认它真能变红。
- **数据库写入脚本**：默认是否只预览、写前备份、写后读回、匹配条件够不够窄、部分失败怎么办。合并代码 ≠ 生产题库已更新，结论里不要混。

### 4. 自己跑测试

- PR 自带的专项测试：本地重跑，报告实际数量（例 7/7）。作者写的数字和你跑出来的不一致就照实写。
- 与改动相关的回归；共享组件改动要覆盖它的其他调用方。
- 需要时写自己的独立探针（暴力枚举、真实快照回放）。改回旧逻辑再跑一次（变异自检），证明测试能抓住问题。
- 环境问题（端口被占、缺浏览器运行时、缓存死锁）和断言失败分开记，不能把没跑成写成通过。命令和常见坑见 `references/review-checklist.md`。

### 5. 浏览器复现原问题

按任务表的复现步骤，在真实组件上走一遍修后的版本：原问题是否消失，正常作答、答错重试、换题是否还正常。本地挂载课件组件的方法见 `references/local-browser-check.md`。截图和页面观察只证明画面，不证明学生学会了。没跑浏览器就不写浏览器结论。

### 6. 出结论，写转发文案

按 `references/feedback-templates.md` 的格式写：

- **通过**：「PR #N 已审核，审核通过」+ 链接 + 问题 / 根因（或修复方式）/ 测试结果。
- **需修改**：「PR #N 已审核，以下问题需修改后再审」+ 链接 + 编号列出有依据的问题，每条一个具体例子（题号、原文、数值、代码位置）+ 一行测试结果。建议另起一段，标清是建议。
- **复审**：「已复核 head `<SHA>`，此前要求修改的 N 项已解决 / 第 k 项仍在」+ 本次复跑了什么。

写完再读一遍：删掉 (d) 类内容；每条问题都能指到具体位置；测试结果只写自己真跑过的，CI 结果单独写「CI：…」。

### 7. GitHub 上的动作分清楚

三件事不是一回事，只有用户明确要求时才在 GitHub 上操作，汇报时说清实际做了哪一件：

- **Ready for review**：团队流程是作者开 Draft，审核人复核通过后由审核人点 Ready。**这一下就是互审签名**（必需检查 `qa-peer-review` 读的就是谁点的 Ready，规则见仓库 `docs/QA_PEER_REVIEW_GUIDE.md`）；作者自己点会判红。需修改时不点，留在 Draft。
- **Approve → Submit review**：在 Files changed 的 Review changes 里提交通过意见。互审不要求它；教授的 Approve 是另一步。
- **只生成文案**：交给用户转发，不代表 GitHub 上已经审过。

不替别人签名、不代填身份字段、不在评论里写「已审核通过」除非用户要求发布。

### 8. 收尾

审完删掉审核目录（`git worktree remove <目录>`，先删软链的 node_modules），不在主仓库留下改动。作者更新后复审时重新跑第 1 步，只核上次的问题和新增的改动。
